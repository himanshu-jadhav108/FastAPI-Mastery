## 📌 Architectural Overview

Calling `SQLModel.metadata.create_all(engine)` is fine for fresh local prototypes, but completely useless once real production data exists. If you add a column, modify an index, or rename a table, `create_all` **does nothing** to existing tables.

**Alembic** provides version-controlled, reproducible, incremental database schema migrations. Every schema alteration is committed as an auditable revision script that can be safely upgraded or rolled back in production without data loss.

```
+-------------------------------------------------------------+
|                      SQLModel Metadata                      |
|                  (Defined in Python Models)                 |
+-------------------------------------------------------------+
                               |
                               | alembic revision --autogenerate
                               v
+-------------------------------------------------------------+
|                     Versioned Migration                     |
|           (e.g., alembic/versions/a1b2_add_due_date.py)     |
|             ├── upgrade(): op.add_column(...)               |
|             └── downgrade(): op.drop_column(...)            |
+-------------------------------------------------------------+
                               |
                               | alembic upgrade head
                               v
+-------------------------------------------------------------+
|                     Production Database                     |
|                   (Live Schema Upgraded)                    |
+-------------------------------------------------------------+
```

## 💡 Core Theoretical Concepts

### 1. Alembic Architecture & Configuration

Alembic utilizes two primary configuration files:
- **`alembic.ini`**: Defines file paths and connection strings:
  ```ini
  sqlalchemy.url = sqlite:///./tasks.db
  ```
- **`alembic/env.py`**: The migration harness script. Point `target_metadata` to your application's `SQLModel.metadata`:
  ```python
  from sqlmodel import SQLModel
  from app.models import Task, User  # Must import models so metadata registers them!
  
  target_metadata = SQLModel.metadata
  ```

### 2. Alembic Command-Line Lifecycle

| Action | Command | Purpose |
| :--- | :--- | :--- |
| **Generate** | `alembic revision --autogenerate -m "Add due_date to task"` | Compares Python models against live DB and creates revision script |
| **Apply** | `alembic upgrade head` | Runs all pending migrations up to the latest revision |
| **Rollback** | `alembic downgrade -1` | Reverts the most recent migration |
| **Status** | `alembic current` | Prints current revision hash recorded in `alembic_version` table |
| **History** | `alembic history --verbose` | Inspects migration revision chronology |

> [!WARNING]
> Always manually inspect autogenerated migration files before running `upgrade head`! Autogenerate cannot reliably detect renamed columns (it may generate a `drop_column` + `add_column`, destroying existing data).

## 🎯 Task Specifications

Inside `project/`, initialize Alembic and execute schema migrations.

### Requirements

1. Inspect `project/alembic.ini` and verify `sqlalchemy.url`.
2. Review `project/alembic/env.py` and confirm `target_metadata = SQLModel.metadata`.
3. Generate the baseline migration:
   ```bash
   alembic revision --autogenerate -m "Initial schema setup"
   ```
4. Apply the migration to the database:
   ```bash
   alembic upgrade head
   ```
5. Modify `project/app/models.py` by adding a new column: `due_date: str | None = None` to `Task`.
6. Autogenerate a second migration:
   ```bash
   alembic revision --autogenerate -m "Add due_date to task"
   ```
7. Apply `alembic upgrade head` and verify the table structure updated without wiping data.

## 🛠️ Step-by-Step Implementation

1. Open your terminal in `18_migrations_alembic/project/`.
2. Verify existing models in `app/models.py`.
3. Run `alembic revision --autogenerate -m "Initial schema"`.
4. Inspect the generated Python file in `alembic/versions/`.
5. Run `alembic upgrade head`.
6. Add `due_date` field, generate the delta revision, and upgrade to head.
7. Test downgrading with `alembic downgrade -1`.
